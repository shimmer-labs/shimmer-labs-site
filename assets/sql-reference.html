Foundations

The skeleton & execution order

Every SELECT is the same clauses in the same written order. Drop the ones you don't need; never reorder.

SELECT     [DISTINCT] columns / aggregates
FROM       table
JOIN       other ON condition
WHERE      row filter
GROUP BY   columns
HAVING     group filter           -- aggregates live here
ORDER BY   columns
LIMIT      n;

Execution order (different from written order)

FROM/JOIN -> WHERE -> GROUP BY -> HAVING -> SELECT -> DISTINCT -> ORDER BY -> LIMIT
The alias wall. SELECT runs late, so a column alias you create there does not exist yet in WHERE, GROUP BY, or HAVING. It does exist in ORDER BY (which runs last). In HAVING, repeat the expression: HAVING SUM(amount) > 1000, not HAVING total > 1000. An alias only becomes a usable column name once the value crosses out into a CTE or subquery.
Reading the wording

Comparison words to operators

Map the phrase to the operator before writing the query. A surprising share of "right logic, wrong result" bugs are > vs >=.

PhraseOperator

at least · X or more · no fewer than>=
less than · under · below · fewer than<
at most · no more than · up to<=
Selecting & sorting

SELECT, WHERE, sort, trim

String matches are case-sensitive and use single quotes: 'East', not "East". ORDER BY ... DESC for newest/highest first; LIMIT n slices after sorting; DISTINCT collapses duplicate rows.

SELECT name, email
FROM customers
WHERE region = 'East';
ExampleThe 5 most recent orders (order_id, order_date, amount):
SELECT order_id, order_date, amount
FROM orders
ORDER BY order_date DESC
LIMIT 5;

DESC = newest. ASC would return the 5 oldest.

Aggregating

Aggregates, GROUP BY, WHERE vs HAVING

Aggregates (COUNT, SUM, AVG, MIN, MAX) crush many rows into one. GROUP BY makes it one number per group. Every non-aggregated column in SELECT must appear in GROUP BY.

WHERE filters rows before grouping. HAVING filters groups after. Aggregates can only go in HAVING. "Regions whose total spend exceeds X" is HAVING. "Only completed orders" is WHERE.
SELECT region, COUNT(*) AS num, SUM(amount) AS total
FROM customers c
JOIN orders o ON o.customer_id = c.customer_id
WHERE o.status = 'completed'      -- rows, before grouping
GROUP BY region
HAVING SUM(amount) > 10000        -- groups, after aggregating
ORDER BY total DESC;
ExampleAverage order amount per region, completed orders only, regions averaging over 200, highest first:
SELECT c.region, AVG(o.amount) AS avg_order
FROM customers c
JOIN orders o ON o.customer_id = c.customer_id
WHERE o.status = 'completed'
GROUP BY c.region
HAVING AVG(o.amount) > 200
ORDER BY avg_order DESC;
Combining tables

JOINs

INNER (JOIN): only rows that match in both tables. LEFT JOIN: every row from the left table, with NULLs where the right has no match.

Join direction. LEFT JOIN keeps all of the left table. The table you want to preserve (e.g. all customers, even those with no orders) goes on the left. Reverse it and rows disappear silently, with no error.
-- count orders per customer; zero-order customers show 0
SELECT c.name, COUNT(o.order_id) AS order_count
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
GROUP BY c.customer_id, c.name;
COUNT trap. COUNT(o.order_id) counts non-nulls, so no-order customers read 0. COUNT(*) would read 1, because the LEFT-join row still exists (padded with NULLs).

Anti-join (rows with no match)

SELECT c.name
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.order_id IS NULL;          -- null-check the key

The same shape on a self-reference finds, for instance, employees who are not managers (no one reports up to them).

Self-join (employee to manager)

SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON m.employee_id = e.manager_id;  -- LEFT so the top of the org still shows
ExampleTotal spend per customer, showing 0 rather than NULL for those with no orders:
SELECT c.name, COALESCE(SUM(o.amount), 0) AS total_spend
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
GROUP BY c.customer_id, c.name;

SUM over no rows returns NULL, so wrap it in COALESCE. (COUNT over no rows is already 0.)

Always-on

NULLs, COUNT, COALESCE

  • NULL equals nothing, not even NULL. Use IS NULL / IS NOT NULL, never = NULL.
  • COUNT(*) counts rows; COUNT(col) skips NULLs. They give different answers.
  • COALESCE(expr, 0) returns the first non-NULL argument. Turns a NULL sum into 0. (This is null-substitution, not casting.)
  • Integer division: 5/2 can be 2. Force float: amount * 1.0 / n or CAST(x AS FLOAT).
  • UNION removes duplicates (slower); UNION ALL keeps everything (faster).
Nesting

Subqueries & CTEs

A subquery is a query whose result feeds another. Three flavors:

-- scalar: returns one value
WHERE salary > (SELECT AVG(salary) FROM employees)

-- list: pair with IN (auto-dedupes; ideal for "has at least one")
WHERE customer_id IN (SELECT customer_id FROM orders WHERE amount > 500)

-- correlated: inner references the outer row, re-runs per row
WHERE e.salary = (SELECT MAX(salary) FROM employees x WHERE x.department = e.department)
Why a scalar subquery for "above average": you cannot write WHERE salary > AVG(salary), because WHERE runs before aggregation. The subquery computes the average separately first, then each row is compared to that one constant.

CTE (WITH) — reusable and readable

WITH big_spenders AS (
    SELECT customer_id, SUM(amount) AS total
    FROM orders
    GROUP BY customer_id
)
SELECT * FROM big_spenders WHERE total >= 1000;   -- total is a column here

Once named, a CTE is used like a table: FROM big_spenders. Reuse it rather than rebuilding its logic.

ExampleCustomers with at least one order over 500 (names only):
SELECT name
FROM customers
WHERE customer_id IN (SELECT customer_id FROM orders WHERE amount > 500);

IN keeps the grain at one row per customer. A JOIN would fan out to one row per qualifying order and need DISTINCT.

ExampleEmployees earning more than their own department's average (correlated):
SELECT e.name, e.department, e.salary
FROM employees e
WHERE e.salary > (SELECT AVG(salary) FROM employees x WHERE x.department = e.department);

"More than" is strictly >. A one-person department equals its own average, so > excludes that person while >= would include them.

Window functions

Window functions

Compute across related rows without collapsing them. PARTITION BY is "GROUP BY that keeps every row," and it is optional (omit it and the whole table is one window). The inner ORDER BY sets the sequence for ranks and running totals.

function() OVER (PARTITION BY group ORDER BY sort frame)

Ranking — the three differ only on ties

FunctionTiesSequence
ROW_NUMBER()never ties1, 2, 3, 4 (arbitrary tiebreak)
RANK()ties share, then skips1, 2, 2, 4
DENSE_RANK()ties share, no skip1, 2, 2, 3

RANK is race medals (two silvers, no bronze). DENSE_RANK is grade tiers (no gaps). ROW_NUMBER is a queue ticket.

SELECT name, department, salary,
       ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS rn,
       RANK()       OVER (PARTITION BY department ORDER BY salary DESC) AS rnk,
       DENSE_RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS d_rnk
FROM employees;

Running total

SELECT order_date, amount,
       SUM(amount) OVER (ORDER BY order_date
                         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total
FROM orders
ORDER BY order_date;

No PARTITION BY means one continuous total. The inner ORDER BY is what makes it accumulate; the last row equals the grand total.

LAG / LEAD — compare to another row

LAG(amount)        OVER (ORDER BY order_date)   -- value from the previous row
LAG(amount, 1, 0)  OVER (ORDER BY order_date)   -- offset 1 (previous), default 0 if none
LEAD(amount)       OVER (ORDER BY order_date)   -- looks forward instead
Offset vs default. In LAG(amount, 1, 0) the middle argument is how many rows back (1 = previous; 0 means the current row, a common bug). The third argument replaces the first row's NULL. Without a default, the first row's LAG is NULL.
Common patterns

Frequently asked patterns

Nth highest (e.g. 2nd highest salary)

WITH ranked AS (
    SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
    FROM employees
)
SELECT DISTINCT salary FROM ranked WHERE rnk = 2;

DENSE_RANK so ties count as one rank. DISTINCT is insurance: harmless when there is no tie, essential when two people share that rank. Rank in a CTE, filter outside, since a window function cannot live in WHERE.

Top-N per group

WITH ranked AS (
    SELECT name, department, salary,
           ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS rn
    FROM employees
)
SELECT name, department, salary FROM ranked WHERE rn <= 2;
The function depends on the noun. "Top N employees" counts people, so ROW_NUMBER gives exactly N. "Top N salaries / tiers, ties included" uses DENSE_RANK and can exceed N. If you must pick exactly N and a tie sits on the boundary, add a tiebreaker so the choice is deterministic: ORDER BY salary DESC, hire_date ASC.

Find duplicates

SELECT email, COUNT(*) AS cnt
FROM customers
GROUP BY email
HAVING COUNT(*) > 1;

Remove duplicates (keep one per key)

WITH d AS (
    SELECT *, ROW_NUMBER() OVER (PARTITION BY email ORDER BY created_at) AS rn
    FROM customers
)
SELECT * FROM d WHERE rn = 1;   -- ORDER BY decides which row survives

Select the whole surviving record, not just the dedup key. ASC keeps the oldest; DESC keeps the newest.

Monthly rollup & period-over-period

WITH monthly AS (
    SELECT DATE_TRUNC('month', order_date) AS month,
           SUM(amount) AS total
    FROM orders
    GROUP BY DATE_TRUNC('month', order_date)
)
SELECT month, total,
       total - LAG(total) OVER (ORDER BY month) AS change_from_prev
FROM monthly
ORDER BY month;

DATE_TRUNC('month', d) flattens every date to the first of its month so they group together. The pattern for "this period vs last" is: aggregate first in a CTE, apply the window (LAG) second. The first month's change is NULL.

Modifying data

DML — change the rows

Always include a WHERE on UPDATE and DELETE, or you hit every row in the table.
-- add rows
INSERT INTO customers (customer_id, name, region)
VALUES (101, 'Acme Co', 'West');

-- change rows; a range filter is common ("rows with id between X and Y")
UPDATE orders
SET status = 'completed'
WHERE order_id BETWEEN 20 AND 100;

-- remove rows
DELETE FROM orders
WHERE status = 'cancelled';

Shape to remember: UPDATE table SET col = val WHERE .... The WHERE is the same row filter as in SELECT.

Defining tables

DDL — define the structure

CREATE TABLE users_roles (
    user_id INTEGER REFERENCES users(id),
    role_id INTEGER REFERENCES roles(id),
    PRIMARY KEY (user_id, role_id)      -- composite key: each pair once
);

ALTER TABLE customers ADD COLUMN phone VARCHAR(20);

DROP TABLE customers;
Conditional logic

CASE & filtered counts

SELECT name,
       CASE WHEN salary >= 100000 THEN 'high'
            WHEN salary >= 60000  THEN 'mid'
            ELSE 'entry' END AS band
FROM employees;

Counting or summing a subset with CASE:

SELECT
  COUNT(*) AS total_orders,
  COUNT(CASE WHEN status = 'completed' THEN 1 END) AS completed,
  SUM(CASE WHEN status = 'completed' THEN amount ELSE 0 END) AS completed_revenue,
  100.0 * COUNT(CASE WHEN status = 'completed' THEN 1 END) / COUNT(*) AS pct_completed
FROM orders;

The 100.0 forces float division so the percentage is not flattened to 0 by integer math.

Before you run

Quick sanity checks

  1. Grain: one row per what? A fanned-out JOIN silently doubles SUMs.
  2. NULL: using IS NULL, not = NULL? COUNT(col) vs COUNT(*)?
  3. Operator: did "more than" become > and not >=?
  4. Integer division: any ratio needs * 1.0 or a cast.
  5. Only what's asked: no extra columns, no filters the question did not request.
  6. Alias placement: not used in WHERE / HAVING / GROUP BY (repeat the expression there).
  7. Tiny example: three rows in your head, does the logic give the right answer?
